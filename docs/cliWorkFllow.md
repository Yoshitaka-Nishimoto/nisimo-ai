同様に、gemini cli でContext管理の層構成を確認する方法
Gemini CLI では公式に「7層モデル」とはうたっていませんが、挙動とドキュメントから、かなり近い層構成を“見える化”することができます。ここでは、質問に挙げた ①〜⑦ の層に沿って、Gemini CLI での確認ポイントを整理します。
​

① 入力層（Context Source）の確認
対話の入力ソースは、おおきく

あなたのプロンプト

開いているカレントディレクトリのファイル・構造

GEMINI.md（グローバル・プロジェクト・ディレクトリ単位の階層プロンプト）

設定ファイル（settings.json などのユーザー／ワークスペース設定）
に分かれます。
​

具体的な確認方法の例

プロジェクトルートやサブディレクトリに GEMINI.md を置いて内容を変え、どのディレクトリで実行したときにどのプロンプトが効くかを /memory 系コマンドや実際の応答で確認する。

ホームディレクトリの ~/.gemini 配下（ユーザー設定）とプロジェクト配下（ワークスペース設定）の両方を用意し、どちらが優先されるか・どうマージされるかを試す。
​

② 選別層（Relevance Filter）の確認
Gemini CLI は、プロジェクト内のどのファイル・情報をコンテキストとして送るかを内部ロジックで選別しています。

確認の仕方（実践的なやり方）

ディレクトリ内にわざとノイズになる大きなファイルや無関係な README を置き、「このファイルの内容について答えて」と聞き、

無視されるのか

一部だけ抜き取られるのか

明示的にファイル指定したときだけ参照されるのか
を観察する。

ファイル数・サイズを増減させ、どのあたりで「関係ないものが落ち始める」かを見て、どのような関連度フィルタが働いているか推測する。

③ 圧縮層（Summarization / Distillation）の確認
長い会話や大きなプロジェクトを扱うとき、Gemini CLI は過去の履歴をサマリ化して文脈を維持します。

確認の仕方

同じセッションで長時間対話し続けた場合、古い会話の細部を覚えているか／要約だけ覚えているかを検証する。

「さっきの会話を一文で要約して」と頼んだとき、かなり前の話が「まとめ」だけになっていて細部が抜けているなら、内部で ChatCompressor 的な要約が走っている可能性が高いです。

プロジェクト内で大量のファイルを読み込ませた後、「さっき読んだ全体を3行で要約して」と促し、モデルがサマリ視点になっているかをチェックする。

④ 構造化層（Task Framing）の確認
Gemini CLI には「対話を 1 ターンごとの Turn オブジェクトで管理する」「プロンプト構造をテンプレート化する」といった層があり、これがタスクの“枠組み”に相当します。

確認の仕方

「このバグを直して」「テストコードを書いて」「設計をレビューして」のようにタスク種別を変えて命令し、

出力フォーマット

ステップ分割（Plan → 実装 → 振り返り）
が変化するかを観察する。

GEMINI.md や設定で「出力形式」「ロール（レビュアー／実装者など）」を変えたとき、すべての応答に一貫した“型”が乗るかどうかを確認し、それを構造化層が担っていると見なす。
​

⑤ 制御層（Orchestration / Policy）の確認
Gemini CLI の内部には、

どのツールをいつ呼ぶか（web 検索・ファイル操作など）

どのモデル／モードを使うか
を決める「オーケストレーション層」があります。

確認の仕方

「Web 検索を使って」「ローカルファイルだけで答えて」などポリシーを変える指示を与え、動きが変わるかを見る。

設定で「特定ツールを無効化」「インターネットアクセスを制限」した上で、同じ質問を投げ、どの情報源が使われているかを比較する。

実行ログやネットワークモニタを使える環境なら、「いつ API コールしているか」「いつ外部ツールを叩いているか」をトレースして、オーケストレーションのタイミングを把握する。

⑥ 実行層（Model + Tools）の確認
ここは最もわかりやすい層で、

LLM そのものの推論

各種ツール（ファイル操作・検索・ビルド／テストなど）の呼び出し
を行います。

確認の仕方

コマンドラインで「実際にどんな CLI コマンドが走ったか」「どのファイルが変更されたか」を git diff などでチェックする。

モデルバージョンやモードを変えて（高速モード／高品質モードなど）、応答速度と質がどう変化するかを観察し、実行層だけ切り替えたときの挙動差を見る。

可能であれば、パケットキャプチャやプロキシを挟み、「どんなペイロードがモデルに投げられているか」を覗くと、⑥に入っている情報（= ①〜⑤を通過した結果）が具体的にわかる。

⑦ 評価層（Feedback / Memory）の確認
Gemini CLI には、セッションをまたいで文脈を持ち越す「メモリ機能」があり、長期プロジェクトでの文脈維持に使われます。

確認の仕方

1 回 CLI を終了し、別のタイミングで同じプロジェクト／アカウントで起動して、「前回話した内容」を覚えているかどうかを試す。

/memory 系のコマンド（表示／追加／リフレッシュ）で、

どの情報が長期メモリとして保存されているか

更新すると応答がどう変わるか
を確認する。
​

「この方針でしばらくやろう」と伝えたあと、数セッション後に同じプロジェクトで作業し、方針が持続しているかを見ることで、評価→メモリ反映の度合いを推測できる。

実務的なおすすめ手順
小さなテストプロジェクトを作り、GEMINI.md・設定ファイル・ノイズファイルを混ぜて、

どの情報が使われるか

どこで要約されるか
を一気に試す。

その結果から、

「これは入力層」「これはメモリ」「これは圧縮タイミング」
とラベルを振った 自分用 7 層マップ を Notion や Markdown に書き出す。

以後は、そのマップを前提に

「この層を自作ツール/MCPで拡張」

「この層はポリシーで縛る」
といった設計をすると、Gemini CLI をかなり意図通りにコントロールしやすくなります。

1. Gemini CLI：GEMINI.md + /memory の最小実験
1-1. グローバル GEMINI.md とプロジェクト GEMINI.md の優先順
グローバル用 GEMINI.md を作成（なければ作る）

bash
mkdir -p ~/.gemini
cat << 'EOF' > ~/.gemini/GEMINI.md
あなたは常に関西弁で話すアシスタントです。
EOF
プロジェクト用 GEMINI.md を作成

bash
cat << 'EOF' > GEMINI.md
あなたはこのプロジェクトでは、常に「敬体の標準的な日本語」で話します。
EOF
プロジェクトディレクトリで Gemini CLI を起動

bash
gemini
実験プロンプト

「このプロジェクトでは、どんな話し方をするように指示されていますか？」

「いまの説明を 1 行で要約してください。」

→ ここで敬体の標準日本語になっていれば、「プロジェクト GEMINI.md がグローバルより優先された」と判断できます。

1-2. /memory 経由で GEMINI.md がどう読まれているか確認
対話プロンプト gemini > 上で、次を実行します。

現在のメモリ（= 読み込まれた階層プロンプト）の確認

text
/memory show
出力に「グローバル GEMINI.md」「プロジェクト GEMINI.md」相当の内容が両方含まれているかを見る。

どちらが「上書き」されているか／どちらが「追記」されているかも観察ポイントです。

GEMINI.md を書き換えて再読み込み

bash
cat << 'EOF' > GEMINI.md
あなたはこのプロジェクトでは、常にターミナル中心の開発者支援に特化して応答してください。
EOF
対話プロンプトで:

text
/memory refresh
/memory show
/memory refresh 後に /memory show の内容が変わっているかを確認します。

そのうえで「このプロジェクトでのあなたの役割を説明してください」と聞き、応答内容が新しい GEMINI.md に沿っているかを見ると、「評価層 → メモリ更新」の動きが分かります。

一時メモリの追加実験

text

その後:

「README の内容を要約してください」と指示し、先頭に「【実験中】」が付くか確認。

別セッション（Gemini CLI を一度終了して再起動）で同じ指示をして、付かなくなっていれば「セッションメモリ」扱いと判断できます。

2. Cursor：GEMINI.md 相当のコンテキストと記憶の実験
Cursor 側は「GEMINI.md」という名前ではなく、ワークスペース設定・エディタ拡張・エージェント設定に埋め込む形になります（以下は一般的なワークフローベースの例）。

2-1. ワークスペース単位のシステムプロンプト
gemini-context-test を Cursor で開く。

ワークスペース設定（settings.json や Cursor の設定 UI）で、対象プロジェクトに対する「Assistant のデフォルト指示」を記述。例えば:

text
// 擬似例：Cursor の設定で「Project Instructions」などに書く
{
  "projectInstructions": "このプロジェクトでは、常に日本語で、ターミナルで実行できる具体的なコマンドを優先して提案してください。"
}
実験プロンプト

「このプロジェクトであなたが守るべきルールを、箇条書きで説明してください。」

「README.md を要約してください。その際、ターミナルで実行可能なコマンドも 1 つ提案してください。」

→ ここで「コマンド提案」が継続的に出るなら、Cursor のワークスペース設定が「GEMINI.md 相当の長期コンテキスト」として効いていると見なせます。

2-2. ファイルベースのコンテキスト確認（入力層＋選別層）
プロジェクトにルールファイルを追加:

bash

- JavaScript のコード例は基本的に使わないこと。
EOF
README からは言及せずに、エディタで README と PROJECT_RULES を開いた状態で、Cursor に対して:

「このプロジェクトで新しいサンプルコードを書くとき、どの言語を使うべきですか？」

「README をもとに、サンプルコードを 1 つ書いてください。」

→ TypeScript が選択されるなら、「開いているファイルが強くコンテキストを形成している」と判断できます。
→ PROJECT_RULES を閉じて同じ質問をすると挙動が変わるかどうかも確認すると、選別層（Relevance Filter）の効き方が見えます。

git work treeについて、最新の概念とツールについて教えて。
git worktree は「1つのリポジトリ（.git）」に対して複数の独立した作業ディレクトリをぶら下げる仕組みで、AI 駆動開発やエージェント並列実行と相性が良い“最新ワークフロー用の土台”になっています。 2015 年（Git 2.5）以降の機能ですが、ここ 1〜2 年で AI ツールとの組み合わせ前提で再評価されている、というのが現在のトレンドです。
​

概念の整理（いまの捉え方）
履歴は 1 つ、作業机は複数
.git ディレクトリに履歴・オブジェクトは一元管理され、各 worktree は「ワーキングツリー／インデックス／HEAD だけが独立した作業机」という位置づけです。
​

ブランチ単位の“物理分身”
通常は 1 ディレクトリで git switch しながら作業するところを、worktree では my-app-main, my-app-hotfix, my-app-feature-x のようにディレクトリを分け、各ディレクトリに別ブランチをチェックアウトして並列作業できます。
​

同じブランチを複数 worktree に出せない
ブランチは「どの worktree に紐付いているか」を Git が管理しており、同じブランチを別の worktree でそのままチェックアウトすることはできません（それを内部構造から丁寧に説明する記事も増えています）。
​

基本コマンド（2026 時点でも定番）
作業中リポジトリの一覧

bash
git worktree list
既存ブランチの worktree を追加

bash
git worktree add ../my-project-feature-a feature/a
ブランチ作成＋ worktree 作成を同時に

bash
git worktree add -b feature/new-ui ../my-project-new-ui
使い終わった worktree の削除

bash
git worktree remove ../my-project-feature-a
これらの流れ（追加 → 作業 → コミット → 削除）を一通り説明したチュートリアルが多く、AI 駆動開発でもこのパターンがベースになっています。
​

最新トレンド：AI/エージェントとの組み合わせ
AI コーディングエージェントの「作業領域分離」に使う
複数のブランチを別ディレクトリに出して、エージェントごと・タスクごとに worktree を割り当てることで、変更の衝突や誤編集を避ける、という使い方が紹介されています。
​

Claude Code / Gemini CLI / 他ツール側の対応
「各 worktree を別セッションとして扱う」「各 worktree で別のコンテキスト・エージェントを動かす」といった使い方がガイドやブログで推奨されており、git worktree が AI 開発フローの前提ツールの一つとして解説されるケースが増えています。
​

ghq や fzf との連携
ghq + git worktree + fzf でタスク／ブランチ／worktree を高速に切り替え、そこに AI エージェントをアタッチする開発スタイルも紹介されており、「タスクごとに worktree を用意してエージェントを走らせる」という発想が定着しつつあります。
​

実務でのおすすめパターン
大きなタスク用のメイン worktree＋緊急対応用のサブ worktree
main ブランチを含む従来の作業ディレクトリとは別に、hotfix ブランチ用の worktree を用意し、テストやビルドを並列で回すパターンがよく使われています。
​

フロント／バックエンド／インフラを worktree で分割
feature/frontend, feature/api, feature/database のようにブランチとディレクトリを分け、それぞれに別エージェント・別サーバーを担当させる事例もあります。
​

ワークスペースの軽量化
完全クローンを複数作るよりディスクを大幅に節約できるため、「モノレポを worktree で刻んで AI エージェントに渡す」という運用が現実的になっています。
​

まとめのポイント
git worktree 自体は新機能ではないが、「履歴共有＋作業状態だけ分離」というコンセプトが、2025〜2026 年の AI 駆動開発・複数エージェント開発の標準テクニックとして再注目されている。
​

最新の文脈では、単なる「便利な並列ブランチ機能」ではなく、「エージェントや IDE／CLI を安全に並列実行させるための“物理的サンドボックス”」として捉えると設計がしやすい、という位置づけになっています。

​Gemini CLIのmemory resumeは、保存した会話セッションを再開するための機能です。主に/chat resume <タグ名>コマンドで使用され、以前の会話履歴を指定したタグから復元します。
/chat save "conrextついて2026-01-16" <タグ名>
/chat resume "conrextついて2026-01-16" <タグ名>
主な違い
memory resume: プロジェクトの背景知識やルールを自動/手動でリフレッシュ。起動時や/memory refreshで頻用され、全体コンテキストを維持。
​
/chat resume <タグ>: /chat saveでタグ付けした特定会話を復元。/chat listで一覧確認後使用し、タスクごとの議論を素早く再開。
​
使い分け例
開発中はmemory resumeで基盤知識を保ち、/chat resumeでコードレビューなどの個別議論を切り替え。両者を併用すると効率的です。
